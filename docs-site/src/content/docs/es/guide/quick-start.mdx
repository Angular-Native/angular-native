## Qué hace falta

<Tabs syncKey="platform">
  <TabItem label="iOS · tvOS · visionOS">
    Xcode con el runtime de simulador de la plataforma que quieras. tvOS y
    visionOS traen el suyo aparte: `xcodebuild -downloadPlatform tvOS`.

    tvOS, visionOS y watchOS piden además un toolchain nightly de Rust: sus
    targets son de nivel 3 y no traen `std` precompilada.

    ```bash
    rustup toolchain install nightly
    rustup component add rust-src --toolchain nightly
    ```
  </TabItem>
  <TabItem label="Android · Wear OS">
    El SDK de Android, que se encuentra por `ANDROID_HOME` o donde suele estar,
    y el NDK. Aquí no hay Gradle: `an` llama él mismo a `aapt2`, `javac`, `d8`
    y `apksigner`.

    Las dependencias de Material 3 se resuelven una vez:

    ```bash
    python3 scripts/fetch-android-deps.py
    python3 scripts/prepare-android-deps.py
    ```
  </TabItem>
  <TabItem label="macOS">
    Las herramientas de línea de comandos de Xcode y nada más. No hay
    simulador: la app corre en la máquina donde la compilas.
  </TabItem>
</Tabs>

## Instalar el CLI

<Steps>

1. Deja `an` en el PATH:

   ```bash
   npm install -g @angular-native/cli
   ```

   <Aside type="note">
   El paquete lleva el SDK además del ejecutable —el Swift y el Java de las
   shells, el Rust del core, el TypeScript del framework—, así que no hay nada
   que clonar ni ningún `AN_HOME` que definir. Lo que no lleva es un core
   compilado: los comandos de plataforma lo construyen con tu propio `cargo`, y
   [Instalar el CLI](/es/guide/installing/) cuenta qué hace falta para eso y por
   qué.
   </Aside>

2. Crea un proyecto de Angular, o usa uno que ya tengas:

   ```bash
   npx @angular/cli@latest new mi-app
   cd mi-app
   ```

3. Prepáralo:

   ```bash
   an init
   ```

   Añade un manifiesto, un tsconfig para el build nativo, los dos paquetes del
   framework y un punto de entrada nativo. No toca ni `src/main.ts` ni
   `angular.json`, así que `ng build` y `ng serve` siguen funcionando
   exactamente igual que antes.

4. Añade una plataforma y arráncala:

   <Tabs syncKey="platform">
     <TabItem label="iOS · tvOS · visionOS">
       ```bash
       an add ios && an ios
       an add tvos && an tvos .
       an add visionos && an visionos .
       ```
     </TabItem>
     <TabItem label="Android · Wear OS">
       ```bash
       an add android && an android
       an wearos .
       ```
     </TabItem>
     <TabItem label="macOS">
       ```bash
       an macos .
       ```
     </TabItem>
   </Tabs>

   <Aside type="tip" title="Por qué el punto al final">
   `an ios` y `an android` recaen en el proyecto donde estás. Los otros cinco
   llevan de serie un ejemplo de este repositorio, y fuera del monorepo nombrar
   cualquier directorio que no sea la raíz del proyecto es un error — así que
   con `.` compilan el tuyo.
   </Aside>

</Steps>

## Desarrollar con refresco en caliente

```bash
an dev              # simulador de iPhone
an dev --android    # emulador de Android
an dev --tvos       # simulador de Apple TV
an dev --visionos   # simulador de Vision Pro
an dev --watchos    # simulador de Apple Watch
an dev --wearos     # emulador de Wear OS
an dev --macos      # una ventana en este mismo Mac
```

`--macos` es el distinto: no hay simulador, así que la app se abre en la máquina
que la está compilando y el servidor con el que habla está en esa misma máquina.

Al guardar un componente, su definición se cambia en la app que está corriendo.
Te quedas en la misma pantalla, con lo que hubieras escrito y los temporizadores
en marcha.

<Aside type="caution" title="Lo que cuesta un guardado que no es de un componente">
Tocar el propio framework —`packages/platform-native`, `packages/primitives` o
una dependencia— no se puede coser en caliente: en el intérprete solo cabe una
copia de Angular. La app se reinicia ahí mismo, vuelve con el código nuevo y
pierde el estado de los componentes. No hay nada que matar ni nada que volver a
lanzar: el cambio se ve en el fotograma siguiente.

`packages/runtime/runtime.js` es el único fichero que ninguna recarga puede
llevar. El preludio se compila dentro del binario nativo en vez de servirse en
el bundle, así que `an dev` vuelve a construir la app y la deja otra vez en el
simulador en lugar de ofrecer una recarga que no cambiaría nada. Tarda lo que
una compilación normal, y es lo único que mete un preludio nuevo en el
dispositivo.

Rust y los shells de Swift y Java no se vigilan: para eso están `an ios`,
`an macos` y los demás.
</Aside>

## Tu primera plantilla

```html
<an-view [style.padding]="'16'" [style.gap]="'12'">
  <an-text [fontSize]="28" [fontWeight]="'bold'">Ajustes</an-text>

  <an-view [style.flexDirection]="'row'" [style.justifyContent]="'space-between'">
    <an-text>Notificaciones</an-text>
    <an-switch [on]="avisar()" (onChange)="avisar.set($event)" />
  </an-view>

  <an-button
    [title]="'Guardar'"
    [variant]="'filled'"
    [accessibilityHint]="'guarda sin salir de la pantalla'"
    (press)="guardar()" />
</an-view>
```

Ese `an-switch` es un `UISwitch` en iOS y un `MaterialSwitch` en Android. El
layout es flexbox, calculado una vez en el núcleo y entregado a cada plataforma
como marcos absolutos.
